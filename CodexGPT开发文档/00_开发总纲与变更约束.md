## 1. 开发目标与当前边界

ElementWar 是 Unity 2022.3.62f3、URP 14.0.12 的第三人称射击原型。开发优先方向为：

1. 3C：角色移动、相机、瞄准、射击和动作手感。
2. 性能：避免不必要的运行时分配与重复实例化，保持现有子弹/特效池的复用策略。
3. 网络：PVP 的 UDP 权威模拟、预测、插值与协议一致性。
4. 渲染：保持 URP 和既有模型材质兼容。

当前有两条必须隔离的运行路径：

- **PVE**：`GameStart.unity → PVEGame.unity`。三名可切换角色、随从 NavMesh、敌人 AI、真实 CharacterController 碰撞、状态机与投射物。
- **PVP**：`GameStart.unity → PVPGame.unity`。单角色、本地预测 + 服务端权威；`PvPMotor` 直接驱动 Transform，PVE 状态机和随从 AI 必须禁用。

`New Scene.unity` 与 `Assets/Scripts/FPS/` 是 Hunter/FPS 实验沙盒，不是当前构建入口。除非需求明确指向该沙盒，不应把实验代码接入 PVE/PVP 主流程。

### 1.1 产品愿景与范围

ElementWar 的目标是一个以**二次元渲染、角色表现与竞技射击手感**为核心的 PC 第三人称射击项目。体验方向参考《卡拉彼丘》的二次元竞技 TPS，但不复刻其具体角色或关卡，且当前不实现“弦化/纸片化”机制。

数值体系、二次元美术风格与表现方法可在明确用途、范围及权利边界后作为研究或局部复现对象；不能将参考资料、受保护资产或未授权内容直接并入项目。近期不以扩充 PVE 内容量为优先级。

- **PVE 定位**：单机验证环境。低成本验证角色操作、武器、敌人反馈、动画、特效、镜头及二次元渲染，成熟的可复用表现再接入 PVP。
- **PVP 定位**：长期核心方向。目标是建设具备商业多人 TPS 基本工程特征的对战原型：服务端权威、客户端预测、快照同步、远端插值、延迟补偿、命中判定、死亡重生、计分及对局流程。
- **“对标商业开发”的含义**：先对标核心网络正确性与操作反馈，再对标角色差异、战斗节奏和视觉一致性；不承诺在近期实现匹配、反作弊、账号、运营、云部署等完整商业服务体系。

### 1.2 模块目标与验收标准

| 模块 | 目标程度 | 验收标准 |
|---|---|---|
| 角色 3C | 建立稳定的二次元 TPS 基础手感 | 走、跑、冲刺、跳跃、空中控制、滑铲、瞄准连续切换；斜坡、边缘、切角色和死亡接管无明显状态跳变或位移冲突。 |
| 相机与瞄准 | 镜头兼顾角色展示与射击可读性 | 常态/瞄准切换不跳镜；准星、枪口、命中点逻辑一致；镜头遮挡和穿模可控；后坐力、受击、冲刺反馈可调。 |
| 武器与射击 | 形成可调的战斗表现层 | 每种武器具有明确射速、散布/后坐力、命中反馈、曳光、枪口火焰、音效与命中特效；PVE/PVP 可共享视觉，不共享伤害权威。 |
| 角色差异 | 形成可读且可平衡的基础差异 | 至少体现不同角色的移动、瞄准、武器或技能倾向；差异不破坏统一的 PVP 网络移动模型。 |
| PVE 验证场 | 成为快速迭代验证环境 | 可验证新角色、新枪、新特效和敌人；敌人具备追击、攻击、受击、死亡与基础出生流程；不以堆叠关卡/任务内容为近期目标。 |
| 敌人与战斗反馈 | 让命中结果清楚可感知 | 敌人有明确的受击、血量、死亡、攻击前后摇和距离判定；玩家可立即理解命中位置与结果。 |
| 二次元渲染 | 建立统一且可扩展的视觉基线 | 角色材质、描边、阴影、光照、后处理、特效与 UI 风格一致；导入模型无紫材质、阴影错误或描边失效等基础兼容问题。 |
| 动画与 IK | 让动作服务射击手感和表现 | 移动、瞄准、射击、滑铲、跳跃衔接自然；持枪角色姿势稳定；Hunter 的无武器基线不因通用改动损坏。 |
| PVP 移动同步 | 达到可对战的基础网络手感 | 本地响应及时、远端平滑、服务端能校正错误位置；高频输入、跳跃、滑铲和瞄准不出现明显抖动。 |
| PVP 战斗权威 | 达到多人 TPS 核心可信度 | 客户端仅提交输入/开火意图；服务端判定命中、HP、死亡、复活和计分；具备延迟补偿，客户端视觉不会造成重复伤害。 |
| PVP 对局闭环 | 完成可重复测试的最小竞技对局 | 大厅、选角、进入比赛、出生、战斗、死亡、重生、比分、胜负结算和返回菜单完整闭环；可进行双人及 bot 验证。 |
| 性能与诊断 | 为扩展提供可观测性 | 对象池稳定；可查看 FPS、帧耗时、网络状态与关键事件；优化以测量结果而非主观感觉验收。 |
| 工程化 | 保持 PVE/PVP 可独立演进 | PVE/PVP 职责不混用；协议两端同步维护；关键数值有统一来源或明确对照；每项改动有最小验证步骤。 |

### 1.3 分阶段开发目标

以下阶段是**后续工作顺序与验收门槛**，不是对现有代码完成度的宣称。现有功能可被归入相应阶段，但只有经运行验证才可标记完成。每阶段涉及 Unity GUI 配置时，由用户执行；Codex 负责代码、操作说明和独立复核。

| 阶段 | 主要代码目标 | 退出标准（必须可验证） | 本阶段不做 |
|---|---|---|---|
| **P0. 加固冲刺（当前前置门槛）** | 先修复会使 PVP 公平性、权威性和预测结果失真的基础问题：服务端 tick 配置一致性、客户端/服务端移动一致性、延迟补偿信任边界、最小 `GameWorld` 自动化测试，以及服务端碰撞方案的技术决策。 | 关键模拟规则可自动验证；客户端预测与服务端在约定输入下结果一致；客户端不能任意扩大延迟补偿窗口；正式 PVP 地图开发前已确定权威掩体/碰撞路径。 | 新角色、技能、地图、模式、HUD 美化、全面架构重构。 |
| 0. 基线与开发纪律 | 明确 PVE/PVP 边界；记录数值、协议、场景入口与验证命令；清除已确认无用的诊断负担。 | 已知风险、事实来源和验收方式可追溯；PVE/PVP 不再因历史文档而引用错误场景或 tick。 | 场景重做、玩法扩张。 |
| 1. PVE 输入与移动内核 | 维护 `PlayerController`、`PlayerModel`、状态机和 CharacterController 的输入、移动、重力、跳跃、冲刺、滑铲、随从切换。 | 主控/随从切换正确；斜坡、边缘、跳跃与滑铲无状态抖动、双重位移或明显穿模；三名角色不回归。 | 新角色技能、复杂敌人、网络复用。 |
| 2. PVE 镜头、瞄准与动画协同 | 完善双 FreeLook、AimTarget、转向、瞄准移动、Animator 参数与既有 IK 权重切换的代码逻辑。 | 常态/瞄准切换无跳镜；准星中心、瞄准点和角色朝向一致；持枪角色动画稳定，Hunter 无武器时无异常。 | 新建/拖拽相机、Rig、Animator 或修改动画资产。 |
| 3. PVE 武器与命中表现 | 完善枪械射速、投射物、防穿透、对象池、曳光、枪口火焰、命中特效、音效事件与可调参数。 | 一套武器可稳定完成“输入→发射→命中/未命中→反馈→回收”；无重复伤害、泄漏或明显对象池失效。 | 弹药经济、换弹、武器收集等内容型系统。 |
| 4. PVE 战斗验证场 | 用敌人 AI、生命/死亡、血条、角色差异和最小 UI 验证战斗节奏；提炼可复用表现接口。 | 玩家能在单机完整验证战斗循环，且能定位问题属于 3C、武器、敌人、动画或渲染；至少一套可调的角色/武器差异方案成立。 | 大型关卡、剧情、任务、刷怪内容量。 |
| 5. 二次元渲染与表现基线 | 代码侧完善 URP 表现适配、运行时特效控制、镜头反馈、可观测性和模型兼容诊断。 | 目标角色在验收场景中无紫材质、基础阴影/描边错误或严重风格割裂；镜头、特效、UI 与角色呈现可一起评审。 | 直接复制受保护的角色、资产或完整美术资源；弦化机制。 |
| 6. PVP 连接、协议与移动预测 | 固化 UDP 握手、输入 tick、60Hz 权威 tick、快照、预测、校正、远端插值及 PVE/PVP 移动隔离。 | 两客户端可进入同局；本地移动及时、远端平滑；跳跃/滑铲/瞄准在延迟或丢包窗口下不出现持续失控。 | 服务器墙体碰撞、匹配和账号系统。 |
| 7. PVP 权威射击与生命周期 | 完善开火意图、服务器 hitscan、历史帧回退、伤害、可靠事件、死亡、重生和计分。 | 客户端无法用本地子弹直接改血；命中、死亡、重生和比分在两端一致；重复/乱序事件不重复结算。 | 复杂技能网络化、大规模人数。 |
| 8. PVP 对局体验与平衡验证 | 接通大厅、选角、出生、HUD、结算、bot 训练；调校角色/武器数值和可读反馈。 | 双人或“真人 + bot”可连续完成多局比赛；胜负条件、返回流程和关键 UI 可用；关键数值有记录和调整理由。 | 多地图、多模式、排位、商业化内容。 |
| 9. 性能、稳定性与回归 | 为热路径建立性能基线，补充诊断、故障处理和可重复验证；降低 `PlayerController` 等高耦合点的改动风险。 | 关键场景可记录帧耗时、网络状态和事件；PVE/PVP 主要流程有回归清单；性能优化有前后测量证据。 | 没有测试/指标支撑的大规模架构重写。 |
| 10. 商业化能力预研（远期） | 在核心对局稳定后，评估房间/匹配、账号、反作弊、服务器部署、监控与版本兼容的技术方案。 | 仅输出有成本、风险和基础设施依赖的技术决策；不将“商业级”作为未验证的完成宣称。 | 直接进入生产运营或承诺完整线上服务。 |

**当前执行顺序**：先完成 P0 加固冲刺，再进入阶段 0 及后续阶段开发。P0 之外的 PVE 观察、问题复现和设计准备可以并行，但不得以新增内容替代 P0 的退出标准。

阶段推进原则：只有当前阶段的完成定义得到运行验证，且没有阻塞性回归，才进入下一阶段。若下一阶段需要 Scene、Prefab、Inspector、Animator、Rig、资源或其他 GUI 配置，Codex 先交付用户操作步骤，收到成功确认后再继续对应代码工作。

**用户操作后的独立复核**：用户完成 GUI 操作并确认后，Codex 不应把口头确认直接等同于配置正确。应根据操作风险，要求或建议提供 Inspector 截图、Hierarchy 路径、Console 输出、运行结果或可读取的配置证据；再独立检查引用、参数、日志和行为是否与目标一致，并给出必要的修正建议。若证据不足，应将该项标记为“待验证”，不能把它作为后续实现已成立的前提。

**全流程独立工程判断**：Codex 在需求澄清、方案设计、实现、验证和复盘的每一阶段均保持客观，不因用户提出某个想法就默认其合理、成熟或已被验证。发现目标与项目定位冲突、技术风险过高、投入产出不佳、范围失控、违反既有架构边界或不符合常见商业开发实践时，应明确指出具体问题、证据和影响，并至少给出一个可执行的替代方案或渐进式方案。用户保留最终决策权；若仍选择高风险方案，必须记录前提、代价、风险和验收条件，而不是把异议隐藏在实现中。

## 3. 每次改动的强制实施流程

### 阶段 A：定义与定位

1. 写明用户可观察到的目标、影响模式（PVE/PVP/两者）和验收条件。
2. 在 `01_项目基线与结构解析.md` 找到职责模块，再阅读目标目录的 `AGENTS.md` 与相关源码；不得仅按文件名猜测职责。
3. 标出需要同时对齐的边界：动画参数、输入、Prefab/Scene 引用、网络 DTO、服务端常量、资源 GUID 或层/Tag。
4. 先做只读检查，确认工作区已有改动；不得覆盖用户未授权的修改。

### 阶段 B：设计

1. 优先做最小闭环改动，不顺带重构无关系统。
2. PVE 与 PVP 的移动、伤害、生命周期分别建模；只有经验证的共享常量才共享。
3. 若改动触及客户端消息、服务端消息或权威规则，先给出两端字段/语义/tick 的对照，再一起修改。
4. 若涉及场景、Prefab、Animator、Rig、NavMesh 或 TMP 字体，先确定可复现的 Editor 操作或幂等 Wizard；不得手改 `.unity` YAML/二进制内容。

### 阶段 C：实现（仅代码）

1. 代码采用 PascalCase 类型/方法、camelCase 字段、中文必要注释；保留既有 API 的刻意拼写 `StateMechaine`、`Destory()`、`updataAction`，新 API 使用正确拼写。
2. `MyInputSystem.cs` 是生成文件，只改 `.inputactions` 后重新生成。
3. 禁止在热路径用无界 Instantiate/Destroy 替代已有对象池；新增持续运行逻辑必须说明生命周期和退订/释放位置。
4. 任何 null 保护都不能悄悄吞掉核心配置错误；对必须配置的引用保留清晰诊断。
5. **执行边界：除用户明确要求的文档外，Codex 只修改代码文件。**不得通过脚本、Editor Wizard、AssetDatabase、序列化文本或任何间接方式修改 Scene、Prefab、Animator、Rig、模型、材质、音频、字体、Input Actions 或组件引用。
6. 组件拖拽、模型/Prefab 放置、场景搭建、NavMesh 烘焙、Inspector 参数配置、Animator/Rig 配置与其他 Unity GUI 操作均由用户完成。需要这些操作时，先给出精确的 GUI 步骤，再等待用户确认结果；没有确认，不把该配置假定为已完成。用户确认后，按风险给出复核建议并独立验证可获得的证据；证据不足时保持“待验证”状态。

### 阶段 D：验证与交付

按影响范围执行，不以“代码看起来正确”替代验证：

| 影响范围 | 最低验证 |
|---|---|
| 纯 C# / 服务端 | `dotnet build Server/ElementWarServer.csproj`；有协议改动时启动服务端并验证握手/快照。 |
| PVE 玩家、敌人、武器 | Unity 编译无新增错误；运行 `PVEGame` 验证移动、瞄准、射击、受击及对应回归点。 |
| PVP | Unity 编译；`dotnet run --project Server/ElementWarServer.csproj`；至少两客户端或一客户端+bot 验证连接、移动、开火、死亡/重生。 |
| 场景/资源/Wizard | Codex 不执行、不生成用于修改资源的 Wizard 操作；提供用户 GUI 步骤，待用户确认后再继续代码侧工作。 |
| UI/字体/渲染 | 在目标分辨率和实际场景检查，不只依赖 Inspector。 |

交付时必须说明：改了什么、未验证项及原因、是否同步更新本目录文档。

## 4. 不可破坏的运行时约束

### PVE 角色与动画

- `PlayerModel.useFPSMovement=true` 时，水平/垂直移动由 `LateUpdate` 中的 `CharacterController.Move` 执行；`OnAnimatorMove` 丢弃根位移。
- `Animator.applyRootMotion` 仍须保持 `true`，因为现有 Animation Rigging 依赖它求值。不要以关闭 Root Motion 的方式“修复”移动。
- 起跳通过 SphereCast 的 `IsHover()` 判定，落地通过 `cc.isGrounded` 判定；`HOVER_STABILITY_FRAMES = 5` 是斜坡稳定性保护，不应随意改成单帧判定。
- 非主控随从仅由 `NavMeshAgent` 位移；不得同时调用该角色的 `cc.Move`。
- Hunter 当前没有武器与握枪 IK，但保留移动、瞄准状态、瞄准动画和双相机；不能为了修武器系统而误改 Hunter。

### PVE 瞄准、武器与场景

- 瞄准使用两台 `CinemachineFreeLook` 的优先级切换；Impulse Listener 必须在虚拟相机上。
- 荧/芙宁娜的瞄准 IK 需在髋射 TwoBoneIK 与瞄准 MultiAim 间正确切换。修改 Rig data 后，如约束要求，重建 RigBuilder。
- 子弹是 Rigidbody 投射物，并以帧间 Raycast 防穿透；枪口特效/命中特效、子弹各有回收路径。
- `Assets/Scenes/PVEGame.unity` 是当前主 PVE 场景；不要再以不存在的 `Game.unity` 作为目标。所有主场景编辑均由用户在 Unity GUI 完成，Codex 只说明操作步骤并等待确认。

### PVP 权威边界

- 客户端仅提交输入和开火意图；位置、命中、血量、死亡、重生、计分由 `Server/GameWorld.cs` 权威决定。
- `PvPMotor` 与 `GameWorld.SimulatePlayer` 的移动数值必须同步。改速度、重力、跳跃、滑铲或转向前，先查两端实现。
- `Server/Messages.cs` 与 `Assets/Scripts/Network/Transport/NetMessages.cs` 的协议字段与 JSON 命名必须同步；不能只修改一端。
- PVP 默认服务端 tick 为 **60Hz**（`GameWorldSettings.ServerTickRate` 与 `UdpGameServerOptions.TickRate`）。所有以 tick 计时的窗口都需按此换算。
- PVP 没有服务器端场景碰撞；掩体目前是视觉元素。不能把 PVE CharacterController 的碰撞假定带入 PVP。

## 5. 本轮与后续工作的范围管理

本轮已完成建立 Codex 开发文档目录与静态项目基线。本轮起的常规开发仅改代码；Scene、资源和 Inspector/GUI 状态由用户操作。下一轮开始任何功能改动前，都应先从本文件的阶段 A 开始。

当新事实被运行验证推翻时，更新 `01_项目基线与结构解析.md`；当流程或约束变化时，更新本文件，并在修改记录中写日期、原因、影响范围和验证结果。

### 5.1 跨任务交接（强制）

- 每一个新 Codex 任务在完成本文件、`01`、`02`、`03` 与相关 `AGENTS.md` 的阅读后，必须先查看 `03` 的“当前快照”，以它为起点定义本任务范围；不得把旧聊天记录或旧文档叙述直接当作当前事实。

- `03` 的历史记录只追加；“当前快照”允许覆盖更新。对 `项目文档和简历面试等/` 的文档任务不得执行 Git 操作，也不得将该目录作为代码事实来源。
