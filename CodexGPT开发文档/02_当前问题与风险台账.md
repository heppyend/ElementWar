# ElementWar 当前问题与风险台账

> **用途**：记录当前项目中已发现的架构、网络、工程、表现与维护风险，作为 P0 加固冲刺和后续阶段的输入。
>
> **审查范围**：2026-08-21 静态审查源码、项目配置与既有文档；未启动 Unity Editor 或完成双客户端运行验证。本文将“源码已证实”“需运行验证”“远期能力缺口”明确区分。
>
> **使用规则**：风险按对“二次元竞技 TPS + 长期 PVP”目标的阻断程度排序。关闭风险必须附带可复现的验证证据，不能仅凭主观体验或口头确认。

## 1. 当前结论

现有 PVP 已具备 UDP 联机、权威位置/血量/命中、预测校正、远端插值、死亡重生和计分的 **1v1 原型闭环**。但它尚不具备可直接外推为商业多人 TPS 的公平性、可测试性、地图碰撞和扩展能力。

因此，当前不建议优先扩充角色、技能、地图或模式。建议先执行 P0 加固冲刺，再恢复 PVE 3C、表现和 PVP 阶段开发。

## 2. P0：当前前置风险

### R-001：延迟补偿信任了客户端自报参数

| 项目 | 内容 |
|---|---|
| 证据等级 | 源码已证实 |
| 影响 | 竞技公平性、命中可信度、后续反作弊成本 |
| 证据 | `FireRequestMessage` 带有 `estimatedRttSeconds` 和 `interpolationDelaySeconds`；`GameWorld.TryQueueFire` 只校验 Aim 坐标，`ResolveFires` 直接以两者计算历史帧回退。 |
| 风险 | 客户端可在最大回退窗口内自行影响命中回退时间；服务器缺少基于自身测量的 RTT/插值约束。 |
| 建议 | 服务器通过 ping/ACK、输入时间戳或快照序号维护延迟估算；只允许服务端计算并夹紧回退窗口；补充非法/极端/乱序延迟参数测试。 |
| 关闭标准 | 客户端延迟字段不能改变服务器允许的回退范围；测试覆盖正常、高延迟、伪造延迟与重复开火。 |

相关实现：[GameWorld.TryQueueFire](</E:/Unity product/ElementWar/Server/GameWorld.cs:270>)、[GameWorld.ResolveFires](</E:/Unity product/ElementWar/Server/GameWorld.cs:618>)、[服务端 DTO](</E:/Unity product/ElementWar/Server/Messages.cs:43>)。

### R-002：PVP 没有服务端场景碰撞，掩体仅是视觉

| 项目 | 内容 |
|---|---|
| 证据等级 | 源码与项目约束已证实 |
| 影响 | 地图设计、移动合法性、射击遮挡和竞技公平性 |
| 证据 | `GameWorld.SimulatePlayer` 仅处理地面和 `ArenaHalfExtent` 的 XZ 边界；不处理墙体、掩体或场景几何。 |
| 风险 | 客户端视觉掩体不能阻挡权威移动或命中。正式 PVP 地图一旦依赖掩体，玩家看到的规则与服务端规则将冲突。 |
| 建议 | 在制作正式对战地图前选择一个权威碰撞方案：服务器简化 AABB/胶囊碰撞、二维阻挡区、服务器专用碰撞数据或其他确定性实现。先做最小可测原型，再扩展。 |
| 关闭标准 | 至少一种掩体可同时阻挡服务端移动与 hitscan；双客户端在掩体两侧的结果一致。 |

相关实现：[GameWorld.SimulatePlayer](</E:/Unity product/ElementWar/Server/GameWorld.cs:352>)。

### R-003：客户端预测与服务端模拟存在已知漂移点

| 项目 | 内容 |
|---|---|
| 证据等级 | 源码已证实 |
| 影响 | 回弹、抖动、滑铲/边界手感、PVP 调参可信度 |
| 证据 | 服务端会钳制 `ArenaHalfExtent`，`PvPMotor` 本地预测没有同等边界钳制；服务端可通过 `--tickrate` 改 TickLoop 频率，但 `GameWorldSettings.ServerTickRate` 仍保持默认值。 |
| 风险 | 到达边界时本地预测与权威位置不一致；非 60Hz 启动时滑铲、冷却、历史帧等按不同 tick 率计算。 |
| 建议 | 将运行 tick 率设为单一权威来源；为客户端实现相同边界规则；以固定输入录制验证客户端和服务器的位移、跳跃、滑铲、边界输出一致。 |
| 关闭标准 | 60Hz 及支持的可选 tick 率下，测试输入序列的两端结果一致或误差在明确定义的容差内。 |

相关实现：[服务端启动参数](</E:/Unity product/ElementWar/Server/Program.cs:8>)、[服务端移动](</E:/Unity product/ElementWar/Server/GameWorld.cs:352>)、[客户端预测](</E:/Unity product/ElementWar/Assets/Scripts/Network/Client/PvPMotor.cs:85>)。

### R-004：缺少自有自动化测试与回归门槛

| 项目 | 内容 |
|---|---|
| 证据等级 | 静态扫描已证实 |
| 影响 | 所有网络、移动和状态机改动的回归风险 |
| 证据 | 安装了 Unity Test Framework，但未发现项目自有测试程序集或 `Server` 测试项目；`GameWorld` 已是适合单测的零 IO 逻辑。 |
| 风险 | 改动只能依赖人工试玩，无法系统验证输入乱序、边界、冷却、死亡重生、可靠事件和延迟补偿。 |
| 建议 | 先为 `Server/GameWorld.cs` 建立 .NET 单测项目，再逐步补 Unity EditMode/PlayMode 测试；测试与缺陷修复同时增加。 |
| 关闭标准 | P0 的移动、开火、生命周期和协议边界均有自动测试；本地构建可一键运行并阻止明显回归。 |

## 3. P1：进入规模化内容前必须治理

### R-005：网络传输与连接模型仅适合当前 1v1 原型

当前服务器最多接受两名真人；每 tick 以 JSON 向每个客户端发送全量快照。尚无协议版本、账号/会话认证、包大小限制、输入频率限制、匹配或部署策略。

这不是当前 1v1 验证的缺陷，而是明确的能力边界。应将它定位为“权威 1v1 验证层”，不能在没有架构升级的前提下宣称支持商业规模多人对战。

### R-006：游戏规则和数值在多端双写

`PvPMotor` 与 `GameWorldSettings` 分别保存速度、重力、跳跃、滑铲等规则；PVE 也有独立的角色和武器参数。当前依赖注释同步，新增角色、枪械、技能和模式后容易漂移。

建议建立不依赖 Unity 的共享规则定义或版本化数据配置，并对 PVE 表现参数、PVP 客户端预测参数和服务端权威参数做明确分层。

### R-007：运行时动态创建和全局查找过多

PVP 的 NetClient、相机、HUD、大厅和远端实体大量使用 `FindObjectOfType`、`new GameObject` 与运行时拼装。原型阶段开发快，但会隐藏场景配置错误、依赖初始化顺序，并增加 UI/场景维护成本。

建议在进入正式 HUD 和对局流程前，收敛为明确的 Composition Root、依赖注入/注册边界及可重复初始化/销毁流程；不建议立刻全面重写。

### R-008：核心控制器职责过重，模块边界不足

`PlayerController` 同时管理输入、相机、瞄准、IK、角色切换、死亡接管与震动；`NetClient` 同时承担连接、输入、预测、远端管理、事件、开火与部分 Rig 接线。继续增长会导致改一项功能影响多条链路。

建议在 P0 测试建立后，以行为边界渐进拆分：输入采样、相机/瞄准、角色控制接管、网络会话和表现桥接；不要一次性重构。

## 4. P2：目标表现与体验缺口

### R-009：二次元渲染尚无可验收的项目级技术基线

项目已有 URP、MMD 兼容 Shader、Toon 插件和导入经验，但尚未定义项目自己的光照、阴影、描边、色彩分级、角色/场景关系、性能预算和模型兼容标准。当前“二次元风格”更多依赖资源和主观观察。

建议在阶段 5 建立小型视觉验收场景与检查清单；这不等于立即制作大量美术资源。

### R-010：PVE 验证环境的关键射击反馈不完整

玩家受击/死亡动画默认留空；HUD、准星、暂停、弹药/换弹、伤害数字和通用音频体系不完整。它们不必同时实现，但至少应补齐影响镜头、射击与命中节奏判断的最小反馈集合，否则 PVE 无法可靠服务于 PVP 表现验证。

### R-011：场景/组件配置的运行时脆弱性

多个核心类依赖 Inspector 引用和组件存在，例如敌人依赖 NavMeshAgent、血条 Prefab/位置与 UI Canvas；缺失时部分路径没有统一的启动期校验。当前原型可接受，但新增角色/敌人时会出现“进入运行后才空引用”的配置故障。

建议新增代码侧启动校验与清晰错误信息；实际组件拖拽和 Inspector 修正仍由用户在 Unity GUI 完成。

### R-012：文档与当前工作区存在残留漂移

项目基线中仍有已删除 `CLAUDE.md`、已清理诊断组件和旧场景工具流程的描述。它不会直接影响运行，但会使后续“先读文档再操作”的流程建立在过时前提上。

建议在每次代码/架构变更后同步更新受影响文档，并把未运行验证的结论明确标为待验证。

## 5. 推荐执行顺序

1. 执行 P0：建立测试、统一 tick 率与移动规则、收紧延迟补偿、完成碰撞方案最小原型/技术决策。
2. 回到阶段 0：更新事实基线、验证命令和回归清单。
3. 进入阶段 1～5：以 PVE 完成 3C、镜头、武器、战斗与二次元表现验证，不优先堆叠内容。
4. 在 P0 与阶段 1～5 的相关退出标准满足后，进入阶段 6～8 扩展 PVP。
5. 阶段 9 后再评估大规模传输、匹配、账号、反作弊和部署，不提前承诺商业服务能力。

## 6. 风险关闭记录模板

每次关闭或降级风险时，至少记录：

| 字段 | 内容 |
|---|---|
| 风险编号 | 例如 `R-003` |
| 修改范围 | 代码文件、协议、数值或用户 GUI 操作 |
| 验证方式 | 自动测试、服务端构建、双客户端结果、Inspector/Console 证据 |
| 验证结果 | 通过/失败/待验证，附关键现象或数据 |
| 遗留风险 | 未覆盖场景、性能代价、兼容性或后续任务 |
| 日期 | 实际完成日期 |

没有以上证据时，风险只能保持“待验证”或“部分缓解”，不能标记为关闭。
